TASK:
既存の設計書 docs/design-rubric-loop-mcp.md を改訂し、rubric ループを「設計 → 実装計画 → 実装」の
3モードに拡張した版を作れ。
成果物は改訂後の Markdown 設計書1本のみ（実装コードは不要、ただし plugin.json / mcp.json /
ツールの JSON Schema / rubric プリセット / SKILL.md は実物を書く）。
目的は、1つの成果物を収束させるループを、上流成果物が下流の入力になる連鎖として、
モデルの記憶や善意ではなくサーバ側の状態と判定で成立させることである。

追加する3モード:
- design    : 要求から設計書を収束させる（現在の設計書が目指したもの）
- plan      : 確定した設計書から実装計画を収束させる
- implement : 確定した実装計画から実装（コードとテスト）を収束させる

前提（動かせない）:

  黙って変えた箇所が1つでもあれば該当基準を5点以上にしない。
- 配布形態は Agent Plugins 1.0.0 準拠の可搬プラグインパッケージのまま。

  plugin.json と mcp.json の $schema バージョンは一致。stdio の command は単一実行トークン。
  変数展開は args / env の値 / cwd でのみ効き、使ってよい変数は PLUGIN_ROOT と PLUGIN_DATA の2つだけ。

SUCCESS CRITERIA (be strict):
- モードの定義 → design / plan / implement それぞれについて、入力・成果物・成果物の型・
  合格の意味・既定閾値が表になっている。「モードによって少し違う」で済ませない。
- 連鎖の機構 → 上流セッションの確定（FINAL）が下流セッションの入力として固定される仕組みが、
  親セッションのハンドルと成果物ダイジェストの参照として設計されている。
  下流は上流の版を知らないまま開始できない。
- 上流変更の失効 → 上流成果物が確定後に変わった場合、下流の FINAL が失効する経路がある。
  失効の検出（親ダイジェスト不一致）、下流に返る判定、再確認の手順、部分的な再検証で済ませる条件が書かれている。
  「気をつけて運用する」は不可。
- 差し戻し → 下流（実装中）で上流（設計）の欠陥が見つかったときに、上流へ戻す経路が定義されている。
  戻したときの下流セッションの扱い（破棄 / 凍結 / 部分継続）と、監査にどう残るかが決まっている。
- 成果物の型の拡張 → implement モードは複数ファイルの集合が成果物になる。
  単一文字列の content で足りるのか足りないのかを判断し、足りないなら成果物表現をどう拡張するか
  （ファイル集合・マニフェスト・ダイジェストの取り方・サイズ上限）を実物のスキーマで示す。
  plan モードの成果物（タスク分解と依存関係）についても同様に型を決める。
- ツール表面の最小性 → 3モード対応後の全ツールが name / 目的 / 入力 JSON Schema / 出力 JSON Schema /
  エラー条件の表になっている。既存7ツールからの差分（引数追加か新規追加か）が明示され、
  新規追加があるなら1つずつ正当化されている。
- rubric プリセット → モードごとの既定 rubric を実物の JSON で載せる。
  基準ごとに id / 説明 / 重み / 1点・5点・9点アンカー / 検証手段を持ち、
  implement モードでは自動検証（verification:"auto"）の比率が design より高いことが、基準の中身で示されている。
- 実装モードのごまかし対策 → 「テストが通った」という自己申告を、コマンド・終了コード・出力ハッシュ・
  対象コミット/ダイジェストの結合で検証可能にする仕組みがある。
  テストを消す・スキップする・アサートを弱める操作を検出する具体策が書かれている。
  サーバがコマンドを実行しない制約のもとで、どこまで守れてどこから守れないかを正直に線引きしている。
- 状態機械 → 3モードで状態機械が共通か別かを決め、各状態で呼べる／呼べないツールが書かれている。
  モード固有の状態がある場合は、その状態が他モードで到達不能であることが構造的に保証されている。
- 収束と打ち切り → モードごとの最大周回数・停滞窓・停滞閾値の既定値が、それぞれ理由付きで決まっている。
  3モード合計での暴走（設計で12周、計画で12周、実装で12周…）を止める上位の予算と、
  予算超過時のエスカレーション出口が定義されている。
- 永続と再開 → 連鎖の親子関係が PLUGIN_DATA 上でどう表現されるか（ディレクトリ構成の実物）。
  途中のモードから、ハンドル1個で完全再開できる。上流セッションが消えていた場合の挙動も決まっている。
- スキル分割 → skills/ 配下を1スキルにするか3スキルにするかを決め、理由を書く。
  SKILL.md の実物を載せ、モードの選択と遷移をモデルがどう判断するかが書かれている。
  MCPサーバ起動失敗時の縮退動作が3モードそれぞれについて書かれている。
- 監査可能性 → 3モードを貫く監査 JSON のスキーマと、連鎖1本分（design→plan→implement）の実例を1つ載せる。
  第三者が「設計が確定し、その設計から計画が出て、その計画から実装が出た」ことを後から再検証できる。
- 受け入れテスト → 具体シナリオが8本以上（3モード連鎖の正常系1 / 上流変更による下流失効1 /
  差し戻し1 / 実装モードのごまかし検出2 / 予算超過1 / 途中モードからの再開1 / サーバ起動失敗時1）あり、
  呼ぶツール列と期待される返り値まで書かれている。
- 既存設計との整合 → 既存の失敗モード表・ツール表・状態機械・§18 のMCP適合表が、
  3モード追加後も矛盾なく更新されている。更新漏れが1つでもあれば該当基準を5点以上にしない。
  改訂履歴節に「何を足し、何を変え、何を変えなかったか」が列挙されている。
- セルフホスティング検証 → 設計した3モードで「この改訂作業そのもの」をトレースする。
  design モードでこの改訂を回し、続けて plan モードで実装計画を回すところまで、
  呼ぶツール列と返り値で実演する。回らない箇所があれば設計を直す。
- 却下した代替案 → 「モードを分けずrubricだけ差し替える」「3つの別プラグインにする」

  なぜ足りないかを理由付きで棄却している。

LOOP PROTOCOL, repeat every turn:
1. PLAN   - 次の1手だけを述べる。
2. DO     - 設計書を改訂する／良くする。毎周かならず全文を出す（差分だけで済ませない）。
3. VERIFY - 各基準を1-10で採点する。残酷なほど正直に。
            まだ弱い点を具体的に列挙する（「〜が抽象的」「〜の例が無い」まで書く）。
4. DECIDE - 全基準が9以上なら FINAL と出力して停止。
            そうでなければ ITERATING と出力し、最低点から順に直して次周へ。

RULES:
- 全基準が9以上になるまで完了と呼ばない。
- 各周は前回 VERIFY の最低点を必ず動かす。
- 基準そのものを書き換えて通そうとしない。基準は固定、直すのは成果物だけ。
- Agent Plugins 1.0.0 または MCP 2026-07-28 に反する設計は、他がどれだけ良くても該当基準を5点以上にしない。
  仕様が曖昧な点は「仕様に無いのでクライアント任せ」と明記し、そこに依存しない設計にする。

- 私に質問しない。妥当な仮定を置いて進め、置いた仮定は設計書の「前提」節に明記する。
- 「詳細は実装時に決める」で逃げない。既定値を決め切って書く。
