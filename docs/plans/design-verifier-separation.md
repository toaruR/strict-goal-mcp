# 評価の独立分離 (Verifier分離) 設計仕様書

## 1. 背景と課題

### 1.1 現状の課題 (Gemini等の高性能モデルにおける1周終了問題)
`strict-goal` ハーネスを用いたルーブリックループにおいて、Gemini 等のモデルで実行した際に**ループが回らず 1 周（Round 1）で終了してしまう**事象が発生している。

### 1.2 原因の分析
1. **自己評価バイアス (Self-Enhancement / Generosity Bias)**:
   - 成果物を作成したモデル自身に採点（`score_submit`）を行わせると、「要求事項はすべて盛り込んだ」「テストもパスした」という自己肯定感から、全項目に 9 点や 10 点（合格閾値: 9点）をつけてしまう。
2. **批判的検証マインドセット (Adversarial Mindset) の欠如**:
   - 作成コンテキストと同一のコンテキストで評価すると、実装時の思考・仮定を無意識に肯定するため、エッジケース、境界条件、例外系、規約違反、ドキュメントの乖離などの「粗探し」が行われない。
3. **検証プロンプトの機能不全**:
   - 既存の `sg-verifier` 定義はテスト実行やファイルセット生成、コミット・採点の機械的実行のみを指示しており、批判的検証や減点基準が定義されていない。
   - `sg-implementer` や `sg-coder` に至っては `sg-verifier` を介さず自身で `score_submit` を呼ぶフローになっていた。
4. **早期合否判定 (Eager Finalization)**:
   - strict-goal MCP サーバーは、提出されたスコアが `pass_score` (>=9) かつ `pass_weighted_mean` (>=9.0) を満たし、anti-gaming チェックを通過すれば、1周目であっても直ちに `FINAL` を発行する。自己採点が甘いとループによる改善機会が完全に失われる。

---

## 2. 設計方針: 評価の独立分離 (Verifier Separation)

作成と評価の関心事を完全に分離し、**「作成モデルに自己採点させず、批判的検証に特化した独立サブエージェント (`sg-verifier`) に粗探しと減点を担当させる」** アーキテクチャを確立する。

```
+-------------------------------------------------------------+
|               作成コンテキスト (Creator Context)             |
|   - sg-implementer / sg-coder / sg-worker                   |
|   - 成果物 (コード・テスト・設計・計画) の実装と健全性確保       |
|   - 禁止: score_submit の自己実行 (自己採点厳禁)             |
+-------------------------------------------------------------+
                              |
                     成果物 & テスト引き渡し
                              v
+-------------------------------------------------------------+
|         批判的検証コンテキスト (sg-verifier Context)         |
|   - 独立したクリーンコンテキストで起動                       |
|   - ゼロトラスト・有罪推定に基づく徹底的粗探し (Red-Teaming) |
|   - 減点バイアス (Round 1 安易な合格禁止、6〜8点で厳格採点)   |
|   - 具体的な Weakness 特定 & score_submit 実行               |
+-------------------------------------------------------------+
                              |
                         score_submit
                              v
+-------------------------------------------------------------+
|                 strict-goal MCP サーバー                    |
|   - 合否判定 (FINAL / ITERATING / ESCALATED)                |
+-------------------------------------------------------------+
                              |
                     verdict & must_fix
                              v
+-------------------------------------------------------------+
|         作成コンテキストへ差し戻し (Loop の成立)             |
|   - sg-worker 等が must_fix と weakness を解消して再提出    |
+-------------------------------------------------------------+
```

## 3. 詳細設計

### 3.1 役割と責務の分離 (Responsibility Split)

| コンポーネント | 成果物作成 | テスト実装・実行 | artifact_commit | score_submit | 粗探し・減点 |
|---|---|---|---|---|---|
| **sg-worker** | 主担当 (単一タスク) | 主担当 (単体テスト) | 禁止 | 禁止 | 禁止 |
| **sg-implementer** | 統括 (タスク分割) | 統合テスト確認 | 委譲可 | **禁止** (委譲必須) | 禁止 |
| **sg-coder** | 主担当 (直接実装) | 主担当 (直接テスト) | 委譲可 | **禁止** (委譲必須) | 禁止 |
| **sg-verifier** | **禁止** (コード編集不可) | 検証実行 (`helper.js`) | 実行 | **専任** | **専任 (主責務)** |

### 3.2 `sg-verifier` の批判的検証・減点プロトコル

`sg-verifier` は以下の「5大減点規律」に従って採点を行う：

1. **ゼロトラスト・有罪推定原則 (Presumption of Inadequacy)**:
   - 作成者の「問題なく動作する」「要件を満たした」という主張（Rationale）を信じない。
   - 提出された成果物には「必ず見落とし、エッジケースの未考慮、テストの甘さがある」という前提で検査する。
2. **初回合格の原則禁止 (No Easy Pass in Round 1)**:
   - Round 1 において、確実・網羅的なテストと完全無欠な証跡がない限り、9点以上（合格点）を安易に付与してはならない。
   - 初回は 6〜8 点を中心に厳格に減点し、必ず 1 つ以上の `must_fix` をサーバーから引き出して改善ループを強制する。
3. **具体的な粗探し・減点チェックリスト**:
   - **境界値・異常系テストの不足 (-2〜3点)**:
     - 正常系テストしか存在しない、または境界値（0, 空文字, 空配列, null/undefined, 最大長, タイムアウト）のテストが欠落している場合。
   - **エラーハンドリングの粗さ (-2点)**:
     - 例外が型付きエラーでなく汎用 Error で投げられている、エラーが握りつぶされている、スタックトレースやログが不適切。
   - **仕様・規約の軽微な逸脱 (-1〜2点)**:
     - 設計書・計画書に記載された制約、命名規則、`CLAUDE.md` のハマりポイントや規約に準拠していない。
   - **テストアサーションの脆弱さ (-2点)**:
     - 単に `assert(result)` やステータスコードのみで、返却ペイロードや内部状態の変化を厳密に照合していない。
4. **アクション可能な弱点（Actionable Weakness）の義務化**:
   - `weakness` に「なし (none)」「特になし」「将来の課題」等の逃げを禁止。
   - 「関数 `X` の引数 `Y` が空配列の場合の例外テストが未実装」「モジュール `Z` のリソースクローズ処理が未検証」等、次ラウンドで作成者が直ちに実装・テスト可能な具体的弱点を明記する。
5. **批判的証跡の要求**:
   - スコアを付ける際は、欠陥や不足を証明するファイル箇所の `locator` 根拠、またはテストカバレッジ・コマンド出力を提示する。

### 3.3 エージェント定義の改定仕様

#### 1. `.agents/agents/sg-verifier.md` & `.claude/agents/sg-verifier.md`
- ペルソナを「単なる事務ワーカー」から「**批判的検証・粗探し・減点特化の独立ベリファイアー (Adversarial Verifier & Red-Teamer)**」へ昇格。
- 減点チェックリスト、初回合格禁止ルール、アクション可能な弱点記述義務をプロンプトに組み込む。
- ソースコード編集の完全禁止を再確認。

#### 2. `.agents/agents/sg-implementer.md` & `.claude/agents/sg-implementer.md`
- ツール一覧から `mcp__strict-goal__score_submit` を削除または使用禁止と明記。
- 手順4「Commit & Scoring Iteration」を「**Verification Delegation Loop**」へ改定：
  - 実装完了後、コミットと採点は `sg-verifier` を起動して委譲。
  - `sg-verifier` から返された `verdict` が `ITERATING` の場合、指摘された `must_fix` と `weakness` を `sg-worker` に渡して修正・テスト追加を行わせる。
  - サーバーが `FINAL` を返すまで委譲ループを反復する。

#### 3. `.agents/agents/sg-coder.md` & `.claude/agents/sg-coder.md`
- 自己採点を禁止。
- 実装・単体テスト完了後、採点は `sg-verifier` を起動して行わせるプロシージャへ改定。

#### 4. `.agents/skills/strict-goal/SKILL.md`
- 基本原則（Principles）に「**評価の独立分離 (Verifier Separation)**」を明記。
  - 「作成モデル自身に採点させてはならない。自己評価バイアスにより 1 周でループが終了することを防ぐため、採点・評価は必ず批判的検証特化サブエージェント (`sg-verifier`) に委譲せよ。」
- 責務分割表を更新。
- Antigravity / Claude Code における起動例・プロンプト例を追記。

## 4. 期待される効果と検証方針

### 4.1 期待される効果
1. **ループの確実な回転**:
   - `sg-verifier` が 1 周目で厳しい減点（6〜8点）と具体的な Weakness を提示することで、確実に `ITERATING` となり、2周以上の改善ループが回転する。
2. **成果物の品質向上**:
   - 単に「動く」だけでなく、境界値テスト、エラーハンドリング、ドキュメント整合性が反復的に強化される。
3. **モデル非依存性**:
   - Gemini、Sonnet、GPT 等、どのモデルが作成を担当しても、Verifier が独立して厳しく採点するため、モデル固有の自己評価バイアスを排除できる。

### 4.2 検証計画
1. エージェント定義ファイルおよび SKILL.md の構文・整合性検査。
2. `sg-verifier` が想定通り「粗探し」と「減点」を行うかのプロンプト検証。
3. 既存の `strict-goal` テストスイート（`npm test`）が green を維持すること。
