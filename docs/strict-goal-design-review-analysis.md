# strict-goal 設計フェーズにおける品質すり抜け分析と改善指針

## 1. 背景と課題

`docs/spec_strict_goal7.md` は、`strict-goal design` ループを用いて4ラウンドを消費し、総計約1,580万トークン（課金対象約125万トークン、270ターン）を費やして生成された設計仕様書である。
しかし、完了後の短時間のレビューにより、以下のような致命的な設計不備が複数発見された。

### 判明した不備の一覧

1. **`retryAfterMs` の計算式が依然誤り**
   - `previousCount = 0` の場合にウィンドウ境界まで待機するとしているが、境界を越えた直後は現在カウントが前ウィンドウのカウントへスライド（按分）されるため、即座にはリクエストが許可されない。
2. **`maxKeys` が公開 API に未定義**
   - 本文では既定値を `100000` と説明しているが、`Options` インタフェースにフィールドが定義されていない。
3. **既定値の自己矛盾**
   - 「既定値 100000」と「既定は無効（Infinity 相当）」という相反する記述が文書内に共存している。
4. **上限到達時の挙動の矛盾**
   - 「上限到達時に新規キーを拒否する」と「既存キーを FIFO で削除する」という相反するポリシーが同時に記載されている。
5. **計算量の誤り**
   - 最古の `currentWindowId` を探して FIFO 削除する処理は Map の全件走査（$O(n)$）が必要であるにもかかわらず、`consume()` 全体の計算量を $O(1)$ と記載している。
6. **同期 `sweep()` とチャンク処理の両立不能**
   - メソッドシグネチャが `sweep(): number`（同期）であるのに対し、内部処理として `setImmediate` による非同期分割処理を記述しており、同期呼び出し側へ削除件数を返却できない。
7. **時計巻き戻り時の計算基準が未定義**
   - エントリの `currentWindowId` は維持する一方、按分計算における `windowId` の参照先が実時刻側なのかエントリ側なのかが未定義。

## 2. なぜ4ラウンド・1,580万トークンを経てすり抜けたのか？

これらの不備は、深遠なドメイン知識を必要とするものではなく、**「API定義と本文の一致」「アルゴリズムの整合性」「同期/非同期の基礎」といった基本的な設計の破綻**である。
これが高コストな自律ループをすり抜けた背景には、以下の3つの構造的要因が存在する。

### (1) 検証者（Verifier）の「字面チェック病」（Goodhartの法則）
現行のルーブリック基準（`internal_consistency`, `numeric_roundtrip` 等）に対して、サブエージェント（`sg-verifier`）は**「ルーブリックの基準（Anchor）を満たしているように見える表面的な証拠」を機械的に収集する方向に最適化**されていた。
- **例 (`numeric_roundtrip`)**: 往復検算スクリプトを作成して終了コード `0` を確認するが、**そのスクリプト自体が誤った数式モデルを前提に書かれている**ため、欠陥のあるロジックを検証スクリプトがそのまま肯定して満点（9点）をつけてしまう。

### (2) ラウンド修正に伴う「局所パッチ」と仕様のスパゲッティ化
ラウンド1〜3で指摘された `must_fix`（例: 「メモリ上限対策」「上限時の動作」）に対し、Worker は**指摘された箇所のみに限定した局所的な追記・修正**を行った。
その結果、既存の型定義、計算量の記述、エラー処理方針との整合性確認が抜け落ち、**「ラウンドを重ねるほど矛盾が増殖する」という逆転現象**が発生した。

### (3) 自然言語・Markdown に対する機械的制約の欠如
設計が自然言語と Markdown 擬似コードのみで記述されているため、**プログラミング言語のコンパイラや型検査器なら1ミリ秒で検出できる致命的なエラー**（型定義のプロパティ欠落、同期関数内での非同期処理）が、「技術的にもっともらしい文章」として平然と受理されてしまった。

## 3. 「全体を俯瞰したレビュー」と「視点の追加」の是非

### 「全体を俯瞰したレビュー」について
- **安易な追加は逆効果**:
  LLM に対して単に「全体を俯瞰して気になる点をレビューせよ」という抽象的な自由記述指示を与えても、「全体的に整合性が取れており良好です」といった**実効性のない定性的な承認**に終わるか、文体や体裁などの枝葉末節を指摘してループが収束しなくなる。
- **必要なのは「反例探索（Falsification）への具体化」**:
  人間レビュアーが行ったのは「ぼんやり全体を眺めること」ではなく、**「実際にこのAPIを使う／実装する立場での思考実験（Walkthrough / Tracing）」**である。

### 「視点が足りないか（Criteria 不足）？」について
- 単にルーブリックの項目数を増やす（例: 8基準から15基準へ）だけでは、LLM はそれぞれの基準に対する「言い回し」を生成して充足を偽装するため、根本解決にならない。
- 必要なのは、項目の追加ではなく**「既存基準の意味論（Semantics）の先鋭化」と「機械的ガードの導入」**である。

## 4. 改善処方箋

### A. 悪魔の代弁者（Adversarial Falsification / 反例探索）の義務化
Verifier の採点プロセスにおいて、「基準を満たしている証拠を探す」前に、**「この設計が破綻する反例・矛盾・計算量の嘘を最低3点指摘せよ」という敵対的レビュー工程**を必須化する。

具体的には、以下の3つの思考実験を強制する：
1. **時間・状態の遷移トレース**:
   「指定された待機時間だけ経過した直後の境界条件で、本当にリクエストが通るか？」
2. **状態競合の追跡**:
   「上限到達時に新規キーが来た際、拒否とFIFO削除のどちらがどの順序で実行されるか？」
3. **データ構造と計算量の裏取り**:
   「最悪ケースにおいて、採用したデータ構造で本当に表記通りの計算量（$O(1)$）を達成できるか？」

### B. 型定義・契約の機械的検証（Executable Contract）
Markdown 内に含まれる TypeScript のインタフェースや関数シグネチャを自動抽出し、型検査（`tsc --noEmit`）および構文検証を実行する。
- `Options` に `maxKeys` が存在しない場合、それを受け取る実装例やテストコードで即座に型エラーとなる。
- 同期関数 `sweep(): number` 内で非同期処理（`setImmediate` 等）を行う矛盾を構文・型レベルで遮断する。

### C. ラウンド修正時の波及影響監査（Ripple-effect Audit）
ラウンド2以降、`must_fix` に基づいて設計を変更する際、**変更箇所が影響を与える既存要素との整合性マトリクス**の提出を Worker / Verifier に義務付ける。

| 変更・追記要素 | 影響を受ける既存項目 | チェック必須内容 |
| :--- | :--- | :--- |
| `maxKeys` / FIFO削除の追加 | `Options` 型定義、計算量記述、拒否方針 | 本文、型定義、計算量、エラー設計がすべて連動して更新されているか |
| `retryAfterMs` の修正 | 往復検算コード、受け入れテスト | 待機後のスライディングウィンドウ按分計算まで含めてシミュレーションされているか |
| 同期/非同期処理の変更 | 公開 API シグネチャ、戻り値の型 | シグネチャと実行方式（イベントループ制御）に矛盾がないか |

### D. ルーブリック基準（`design.json`）の先鋭化

1. **`internal_consistency` の厳格化**:
   - 単なる「一箇所での定義」にとどまらず、**「Options型定義・本文記述・既定値一覧表の完全一致（型にない設定値や表にない既定値が0件）」**および**「シグネチャと実行モデル（同期/非同期）の完全一致」**を必須要件とする。
2. **`algorithm_soundness`（アルゴリズム・計算量の整合性）の明確化**:
   - 採用したデータ構造の操作から導出される最悪計算量が、明記されたオーダー（$O(1)$, $O(n)$ 等）と厳密に整合していることを検証対象とする。
3. **`numeric_roundtrip` の状態遷移考慮**:
   - 単一の数式代入にとどまらず、**「時間経過に伴う内部状態のスライド（前ウィンドウへの移行）を含めた状態遷移シミュレーション」**を受け入れ条件とする。
