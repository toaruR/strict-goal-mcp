LOOP PROTOCOL, repeat every turn:
1. PLAN   - 次の1手だけを述べる。前周 VERIFY の最低点基準を必ず含める。
2. DO     - 計画 JSON と Markdown を作る／良くする。毎周かならず**全文**を出す（差分で済ませない）。
3. VERIFY - 下の CHECKS を全部実行し、コマンド・終了コード・出力の抜粋を貼る。
            そのうえで各基準を1-10で採点する。残酷なほど正直に。
            各スコアには「点数 / 40文字以上の理由 / まだ弱い点 / 根拠」を必ず付ける。
              - verification=auto の基準の根拠は、実行したコマンドとその出力のみ。
              - verification=manual の基準の根拠は、計画 JSON の該当箇所の引用（タスク id を明示）。
4. DECIDE - 全基準9以上 かつ 加重平均9.0以上なら PASS と出力して停止。
            そうでなければ REVISE と出力し、must_fix（最低点の基準3件を昇順）を挙げて次周へ。

CHECKS（毎周、VERIFY の冒頭で実行する。パスは workspace ルート相対）:
  C1 スキーマ適合:
     node -e '…' もしくは python -c で §19.5.2 のスキーマ検査。
     必須キー欠落・pattern 違反・minItems 違反・additionalProperties を全部落とすこと。
  C2 id 一意性 / 幽霊依存 / 循環 / 孤立:
     jq -r '.tasks[].id' plan.json | sort | uniq -d           # 出力が空であること
     jq -r '.tasks[] | .id as $i | .depends_on[] | "\($i) \(.)"' plan.json  # 参照先の実在確認
     トポロジカルソートを実行し、順序を1本印字する（循環があれば残余タスク id を出す）。
  C3 design_refs の実在:
     jq -r '.tasks[].design_refs[]' plan.json | sort -u を、
     grep -n '^#\{1,4\} ' docs/design-rubric-loop-mcp.md の見出し集合に対して照合し、
     **ヒット0件の参照を列挙する（0件であること）**。
  C4 設計書側からの被覆:
     設計書の §2桁見出しと §19.x / §20.x 小節を列挙し、各々を design_refs が覆っているかを表にする。
     覆われていない節は「実装不要」の判断を計画の assumptions か Markdown に明記していること。
  C5 verify の形式:
     jq -e 'all(.tasks[]; (.verify|length)>=1
              and all(.verify[]; (.command|length)>=3 and (.expect_exit_code|type)=="number"))' plan.json
  C6 粒度:
     jq -r '.tasks[] | "\(.id) \(.estimate_rounds // 99) \(.changes|length)"' plan.json
     estimate_rounds > 3 または changes > 5 のタスクを列挙する（0件であること）。
  C7 被覆の全数表:
     ツール7本 / エラーコード全件 / 失敗モード F1–F20 / 受け入れテスト AT-1–AT-18 について、
     「対応する実装タスク id」「対応するテストタスク id」の2列を埋めた表を出す。空欄0件であること。

RULES:
- 全基準が9以上になるまで完了と呼ばない。PASS はこのプロトコルの語であり、
  MCP サーバが返す `FINAL` ではない。成果物の冒頭に必ず
  `UNVERIFIED-COMPLETE: rubric-loop server unavailable` と書き、
  「マージしてよい」「実装に着手してよい」とは主張しない（§10.3）。
- 各周は前回 VERIFY の最低点を必ず動かす。動かせなかった周は、その理由を明示する。
- 1周で1基準あたり +3 を超えて点を上げない。超えるなら auto 検証コマンド2件以上の出力を根拠に添える。
- 前周と同一の根拠（同じコマンド出力・同じ引用箇所）でスコアを上げない。
  計画が変わっていないのにスコアだけ上げない。
- RUBRIC そのものを書き換えて通そうとしない。基準・重み・閾値は固定、直すのは計画だけ。
  設計書に照らして基準が足りないと気づいた場合は、**基準の追加のみ**許す（削除・重み減・9点アンカーの緩和は禁止）。
- 設計書に無い作業をタスクに足さない。必要だと考えたなら、それは設計書の不足なので
  KICKBACK 節に書く（計画には入れない）。
- 「詳細は実装時に決める」で逃げない。既定値・境界値・ファイル名まで決め切って書く。
- 私に質問しない。妥当な仮定を置いて進め、置いた仮定は計画 JSON の assumptions に明記する。
- 8周（max_rounds）で合格しなかったら STALLED と出力して停止し、
  「どの基準が / なぜ / 人間に何を決めてほしいか」を3行以内で書く。勝手に閾値を下げて終わらない。
