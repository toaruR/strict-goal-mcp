You will work in a loop until the task meets the bar.

TASK:
「rubricループで設計を回すためのMCPサーバ」の設計書を作れ。
成果物は Markdown の設計書1本のみ（実装コードは不要、ただし plugin.json / mcp.json /
ツールの JSON Schema は実物を書く）。
このプロンプト自身がやっている「ワンショットのループ」を、モデルの自制心ではなく
サーバ側の状態と判定で成立させることが目的である。

前提（動かせない）:
- 配布形態は Agent Plugins 1.0.0 準拠の可搬プラグインパッケージとする
  （仕様: https://agent-plugins.org/specification 、クライアント一覧: /compatible-clients ）。
  コンポーネントは skills/ と mcp.json の2種のみ、固定位置でしか発見されない。
- Claude Code はネイティブのプラグイン形式（${CLAUDE_PLUGIN_ROOT} 等）で動かしてよい。
  それ以外のホスト（VS Code / Cursor / GitHub Copilot / ChatGPT & Codex / Kiro ほか）は
  Agent Plugins 準拠側だけで完結させ、ベンダー固有の前提を持ち込まない。
- transport は stdio を既定とし、streamable-http も選べる。legacy SSE には依存しない。

SUCCESS CRITERIA (be strict):
- 潰す失敗モードの特定 → プロンプトだけのループが壊れる具体例（自己採点の甘え、周回中にループを忘れる、
  コンテキスト圧縮で rubric ごと消える、基準を後から緩める、成果物が変わってないのにスコアだけ上がる）を列挙し、
  「どのツール/どの制約でそれを塞ぐか」が1対1で対応している。抽象論だけなら不可。
- ツール表面の完全定義 → 全ツールが name / 目的 / 入力 JSON Schema / 出力 JSON Schema / エラー条件の表になっている。
  ツール同士が直交し、「とりあえず足した」ものが無い。数は最小に寄せる。
- 状態の外部化 → rubric・周回番号・各周のスコアと根拠・成果物の版が サーバ側に永続する。
  セッションIDで完全再開でき、モデルの記憶やコンテキスト残量に依存しない。
  保存先は PLUGIN_DATA（プラグイン更新をまたいで永続する書き込み可能ディレクトリ）に置く。
- 合否判定をサーバが握る → FINAL / ITERATING はモデルの自己申告ではなくサーバの閾値ロジックが返す。
  モデルが「もう十分」と言っても閾値未満なら次周を強制する経路が設計されている。
- 採点のごまかし対策 → 各スコアに根拠（成果物の該当箇所、または検証コマンドとその出力）の添付を必須にし、
  成果物ハッシュが不変なのに点数だけ上がった提出を検出して拒否する仕組みがある。
- rubric のスキーマ → 基準ごとに id / 説明 / 重み / 1点・5点・9点のアンカー記述 / 検証手段（自動 or 目視）を持つ。
  基準の変更は版として記録され、こっそり緩める操作が監査に残る。
- 収束と打ち切り → 最大周回数、停滞検知（N周スコア改善なし）、人間へのエスカレーション出口が定義され、
  無限ループにも早期終了にもならない。閾値と N の既定値まで書く。
- 状態機械の明示 → セッションの状態遷移（初期化→作業→採点→判定→改稿→…→確定/中断）と、
  各状態で呼べるツール・呼べないツールが書かれている。順序違反の呼び出しが構造的に弾かれる。
- 可搬パッケージ準拠 → plugin.json と mcp.json の実物を載せ、$schema のバージョンが両者で一致している。
  stdio の command は単一実行トークン（シェル文字列やパイプ不可、bare name か ./ 始まりのプラグイン相対パス）。
  変数展開は args / env の値 / cwd でのみ効き、command・URL・HTTPヘッダには効かない前提で書けている。
  使ってよい変数は PLUGIN_ROOT と PLUGIN_DATA の2つだけ。cwd は両ディレクトリの外に出ない。
  ヘッダやパッケージ内に資格情報を埋め込まない（1.0.0 に可搬な認証機構は無い）。
- ホスト差の吸収 → Claude Code の ${CLAUDE_PLUGIN_ROOT} は PLUGIN_ROOT のベンダー別名として扱い、
  両方来た場合／どちらも来ない場合の解決順序とフォールバックを決め切っている。
  対応クライアント間の transport 差（legacy SSE の有無）に設計が依存していない。
- スキルとサーバの責務分割 → ループ手順（このプロンプト相当）は skills/ 配下の SKILL.md として同梱し、
  判定・状態・監査はサーバが持つ、という線引きが明示されている。
  MCPサーバの起動が失敗してもスキルは生き残る（コンポーネント障害は非致命）前提で、
  劣化時にループがどう振る舞うか（縮退動作か明示的な停止か）が書かれている。
- 監査可能性 → 全周回のスコア・根拠・成果物差分を JSON で書き出せ、
  第三者が後から「本当に基準を満たしたか」を再検証できる。出力スキーマの実例を1つ載せる。
- 受け入れテスト → 具体シナリオが6本以上（正常収束1 / ごまかし検出2 / 停滞打ち切り1 / セッション再開1 /
  サーバ起動失敗時のスキル単独動作1）あり、呼ぶツール列と期待される返り値まで書かれている。
- セルフホスティング検証 → 設計したツール列で「この設計書自身を作る作業」をトレースし、
  最初から最後まで穴なく回ることを実演する。回らない箇所があれば設計を直す。
- 却下した代替案 → 「プロンプトだけで足りる」「ただのTODOリストMCP」「CIで代用」
  「Claude Code 専用プラグインで済ませる」等を挙げ、なぜ足りないかを理由付きで棄却している。

LOOP PROTOCOL, repeat every turn:
1. PLAN   - 次の1手だけを述べる。
2. DO     - 設計書を作る／良くする。毎周かならず全文を出す（差分だけで済ませない）。
3. VERIFY - 各基準を1-10で採点する。残酷なほど正直に。
            まだ弱い点を具体的に列挙する（「〜が抽象的」「〜の例が無い」まで書く）。
4. DECIDE - 全基準が9以上なら FINAL と出力して停止。
            そうでなければ ITERATING と出力し、最低点から順に直して次周へ。

RULES:
- 全基準が9以上になるまで完了と呼ばない。
- 各周は前回 VERIFY の最低点を必ず動かす。
- 基準そのものを書き換えて通そうとしない。基準は固定、直すのは成果物だけ。
- Agent Plugins 仕様に反する設計は、他がどれだけ良くても該当基準を5点以上にしない。
  仕様が曖昧な点は「仕様に無いのでクライアント任せ」と明記し、そこに依存しない設計にする。
- 私に質問しない。妥当な仮定を置いて進め、置いた仮定は設計書の「前提」節に明記する。
- 「詳細は実装時に決める」で逃げない。既定値を決め切って書く。
