# サブエージェントの入力トークン調査

確認日: 2026-10-18（日本時間）。対象は [codex-session-tokens](2026-10-18-codex-session-tokens.md) に記載された親1件・子32件。

## 集計資料から分かること

- 子32件の Cached Input は 82,608,384、Uncached Input は 2,364,768。子の入力の約97.2%がキャッシュ読み出し。
- Cached Input はリクエストごとの読み出し量の累計であり、起動時に渡した固有の履歴サイズではない。
- `Billed Total = Uncached Input + Output` はこのスクリプト独自の比較指標。キャッシュ入力の料金を含む実際の請求額や、契約上の利用枠消費を示さない。

## 保存ログで確認したこと

ログ: `C:\Users\<user>\.codex\sessions\2026\10\17\` 以下の、資料に記載された各スレッドIDの rollout JSONL。

| 対象 | 確認結果 |

| 設計・実装 supervisor の spawn_agent | 28件すべて fork_turns="all"（失敗等も含む呼び出し数で、子の件数とは別） |

親・設計 supervisor・実装 supervisor・t009・t013 の5件では、重複を除いた last_token_usage の合計と最終 total_token_usage が input / cached input / output の各値で一致した。これらの大きな値は、累積イベントを誤って足し続けたことによるものではない。

資料作成後も親と実装 supervisor の累積値が増えていたため、資料の総計と現在のログ総計は同じ時点の値ではない。上記の資料由来の計算とログ由来の測定は分けて扱う。

## 解釈と対応方針

後続の調査で、none の指定は新規の提案ではなく既存の設計規約だが、今回の Codex 用配布物から欠落していたと確認した。根拠と実際の注入指示の照合は [state-only 委譲監査](2026-10-18-codex-state-only-delegation-audit.md) を参照。

履歴継承を許可する起動設定と、長い子セッションで増えた入力の反復利用を確認できた。ただし、この調査だけでは初回約4万tokensを共通指示・ツール定義・継承履歴ごとに分解できず、fork_turns="none" による削減率も未測定。

対応候補は、子の起動時に fork_turns="none" を明示して skill_state・作業単位・必要パス・出力契約だけを渡すこと、t009のような長い処理を適切な作業単位に分けること、集計に初回入力・リクエスト数・平均入力・fork設定を追加すること。none は親会話の継承を止める設定で、共通指示やプロンプトキャッシュ自体を無効化する設定ではない。

キャッシュの指標とAPI入力料金の関係は [OpenAI公式 Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) を参照。API料金からCodexの契約上の利用枠消費を推定しない。

## 利用枠についての補足

同日、ユーザーから40分未満でリミットに到達したとの報告あり。[公式の利用枠説明](https://learn.chatgpt.com/docs/pricing) では、会話の長さ、推論、ツール利用、検索、キャッシュ等が使用量に影響するとされている。キャッシュ入力を利用枠の消費から除外できる根拠はなく、上記の大量の反復入力・リクエスト数は短時間での枠消費と整合する。ただし、キャッシュの利用枠への換算係数、当時の残量、速度モード等を確認していないため、キャッシュ入力単独の寄与率や40分という到達時間の原因は確定できない。クレジット料金だけでは契約内の利用枠消費は決まらないことも公式に明記されている。
