# 0006 人間の承認はトークンファイルではなくチャットの返答で受け付ける

## 背景
旧方式では、escalate の request_human がサーバ側に秘密トークンファイル(escalations/esc_NN.token)を作っていた。
ユーザーはそのファイルを読み、値をチャットに貼り付けて human_token として渡す必要があった。
一方、設計書 A10 は、トークンを「速度制限であってセキュリティ境界ではない」と位置づけている(認証機構が無いため)。
秘密ファイルを介する手間は、この位置づけに見合わない(推測: コミットに理由の明記なし)。

## 決定
- 承認は、保留中の確認ID(escalation_id)と、ユーザーの返答原文(human_reply)で行う。
- 秘密ファイルの生成・読み取り・貼り付けはしない。
- STALLED・チェーン予算超過・基準緩和・kickback・reopen の全経路を同じ方式に統一する(4bb206d)。
- 確認IDは1回で消費し、返答原文を監査に記録する。

段階的に移行した。
1. STALLED の承認をチャットで受け付け、旧方式と併存させる(6d93e7c)。
2. 全経路をチャットに統一し、トークン方式を撤廃する(4bb206d)。
3. 設計書・計画書の記述を追従させる(b8d85aa)。

## 結果
- ユーザーはチャットで明示的に返答するだけで承認できる。
- 旧パラメータ human_token は拒否される。旧方式の保留記録は、確認IDと返答原文で解決できる。
- 承認の正当性は、引き続き「1人の人間がチェーンを管理する」という前提(A10)に依存する。
- 承認の契約と例は [chat-approval.md](../spec/chat-approval.md)。
