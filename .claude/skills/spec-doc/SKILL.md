ルートリポジトリ(このプロジェクト自身)の変更点を読み取り、プロジェクトの仕様を `docs/spec/specification.md` にドキュメント化してください。前回このスキルで確認したコミットを記録しておき、次回はそれ以降の差分だけを対象にします。

## 前提

- 差分の対象リポジトリ: ルート(このリポジトリ自身。git コマンドは通常どおり `git ...`)。
- 仕様ドキュメントと「最後に確認したコミット」の保存先: ルートの `docs/spec/specification.md`(単一ファイル・追記更新)。
- 最終確認コミットは `docs/spec/specification.md` の frontmatter(`type: spec`)の直後の行に、次の形式のマーカーで記録する(frontmatter が無い旧形式のファイルでは先頭行):
  ```
  <!-- spec-doc:last-reviewed-commit=<commit-hash> reviewed-at=<YYYY-MM-DD> -->
  ```

## 手順

1. **前回確認コミットを取得する**
   `docs/spec/specification.md` を読み、`spec-doc:last-reviewed-commit` マーカー(frontmatter の直後、旧形式なら先頭行)からハッシュを取得する。
   - ファイルが無い、またはマーカーが無い場合は **初回** として扱う(後述)。
   - 旧パス `docs/specification.md` しか無い場合は、知見記録キットの再インストール(`update-kit`)で新パスへ移動してから実行するよう伝えて終了する(勝手に移動しない)。

2. **現在の HEAD を取得する**
   `git rev-parse HEAD` で現在のコミットを取得する。
   - 前回確認コミットと一致する場合は「前回から新しい変更はありません」と伝えて終了する。

3. **差分を把握する**(並行実行)
   - 通常: `git log --oneline <last>..HEAD` と `git diff <last>..HEAD`
   - 初回(マーカー無し): `git log --oneline -20` と、現状を俯瞰するため主要ディレクトリ(`scripts/`・`src/` 等)の構成を `git ls-files` 等で確認する。
   - 差分が大きい場合はファイル単位で `git diff <last>..HEAD -- <path>` に分割して読む。

4. **コンテキストを読み込む**
   仕様を正確に書くため、関連ドキュメントを参照する。
   - `CLAUDE.md`(アーキテクチャ・ハマりポイント・知見)
   - `AGENTS.md`
   - `docs/` 配下の関連ファイル(実装計画・タスク管理など)
   - 既存の `docs/spec/specification.md` の内容(重複記述を避け、整合させる)

5. **仕様を抽出してドキュメント化する**
   コミットメッセージと diff から「**何が・どう振る舞うか**」という仕様を読み取る。実装の手順ではなく仕様・挙動・設計意図を書く。
   いきなり文章にせず、**事実の列挙 → 文体の適用 → 欠落チェック** の 3 段階で書く(読みやすさのための書き換えで情報が落ちるのを防ぐため)。

   - **a. 事実を 1 行 1 個で列挙する**: diff から読み取れる仕様上の事実を、作業メモとして 1 行 1 事実で書き出す(ファイルには書かない)。「どの対象が・どの条件で・どうなるか」が 1 行で完結する粒度にする。
   - **b. 対象ごとに節へ振り分けて文章化する**:
     - 画面 / API エンドポイント / データモデル(db.json) / 公開(HTML 書き出し) / 設定 など、対象ごとに見出しを分けて記述する。
     - 追加された機能は新しい節として追記、既存仕様の変更は該当節を上書き更新、削除された機能はその旨を反映する。
     - 文体は後述「文体ルール」に従う。
   - **c. 状態遷移・処理フローは図にする**: 状態が 3 つ以上ある、または分岐を含む処理の流れが追加・変更された場合は、文章に加えて Mermaid 図(`flowchart` または `stateDiagram-v2`)を該当節に置く。
     - 1 図の要素(ノード)は **8 個以内**。超える場合は図を分割するか、粒度を上げて要約する。
     - 図は文章の要約であり、図にしか書かれていない事実を作らない(細部は文章側に書く)。
   - **d. 欠落チェック**: a で列挙した事実を 1 個ずつ照合し、すべてが本文(または既存の節)に反映されているか確認する。抜けていたら追記する。件数(列挙 N 件 / 反映 N 件)を手順8で報告する。
   - 不明点(diff だけでは意図が読めない箇所)は推測で断定せず「要確認」として明示する。

   **文体ルール**(航空整備向けの簡易技術英語 ASD-STE100 の原則を、日本語に**8割程度の厳しさ**で適用する。厳格に適用すると情報が落ちやすいため、事実を削るくらいならルールを緩める):
   - 1 文 1 事実。1 文は目安 40 字以内。読点でつなげた長文は分割する。
   - 主語(何が)を明示する。「〜される」より「X が〜する」を優先する。
   - 1 語 1 義。同じものを別の言葉で呼ばない。逆に、別のものに同じ言葉を使わない。既存 `docs/spec/specification.md` の用語に合わせる。
   - 二重否定(「〜しないわけではない」等)を使わない。
   - 1 段落は 6 文以内。手順や条件の並びは箇条書きにする。
   - 用語が新たに増えた場合は、`docs/spec/specification.md` 末尾の「用語集」節(無ければ作成)に 1 行で定義を追加する。

6. **`docs/spec/specification.md` を更新する**
   - マーカーを今回の HEAD ハッシュ・本日の日付(CLAUDE.md の currentDate)に更新する。frontmatter は残し、マーカーはその直後の行に置く。
   - 初回でファイルが無い場合は、frontmatter(`type: spec` / `owner: ai`)+ マーカー + `# 仕様書` 見出し + 対象別の節という構成で新規作成する。
   - 本文は日本語で、既存 `docs/` のトーンに合わせる。

7. **`CLAUDE.md` の「ハマりポイント」を最適化する**
   このセクションは知見の記録ルールにより都度追記される運用のため、肥大化・重複・陳腐化が起きやすい。**目標: `CLAUDE.md` はファイル全体で 25KB 未満に保つ**(`wc -c CLAUDE.md` で確認)。今回の diff で触れた範囲を中心に、以下 5 種類の最適化を行う。

   - **a. 重複・類似項目の統合**: 同じ原因・同じ対処を指す複数の項目を 1 つにまとめる。内容は欠落させず、具体例や参照先はすべて残す。
   - **b. 陳腐化した項目の検出**: 今回の diff で変更・削除されたファイルや機能に関連する既存項目があれば、該当コードが今も同じ挙動かを `grep`/`git diff` などで確認する。
     - 明確に解消済み(該当コード・設定が削除／修正済み)と確認できた場合のみ削除する。
     - 判断がつかない場合は**自動削除しない**。文末に `(要確認: 現状と一致するか未検証)` を付記し、手順8の報告に列挙する。
   - **c. 長大化した項目の `docs/` への分割**: 1 項目が目安 300〜400 字を超えている場合、詳細を対応する `docs/` 配下の文書(仕様・設計なら `docs/spec/`、手順・原理解説なら `docs/guides/`。CLAUDE.md の「ドキュメント配置ルール」に従う)に移し、`CLAUDE.md` 側は 1〜2 行の要点 + `→ 詳細: @docs/xxx.md` のリンク形式に圧縮する(既存の `docs/*.md` 群の参照パターンに合わせる)。移し先の判断基準:
     - 既存の `docs/*.md` に明確に対応するテーマがあればそこに追記する(新規ファイル作成は避ける)。
     - どの既存ファイルにも当てはまらない新しいテーマの場合のみ、新規ファイル(frontmatter 付き)の作成をユーザーに確認する。
   - **d. 既存 docs との重複圧縮**: `docs/` 配下の各ファイルを横断的に確認し、ハマりポイントの項目と**同じ内容がすでに詳しく書かれている**箇所があれば、CLAUDE.md 側は 1〜2 行の要点 + リンクに圧縮する(c と同様の圧縮だが、"今回新たに移す" のではなく "すでにどこかにある内容の重複を消す" 点が異なる。過去の記録時に docs 側へ移し忘れた項目や、後から docs 側に詳細版が書かれて二重管理になった項目を拾うのが目的)。
   - **e. 表現の簡潔化・文体統一**: 項目数・内容は変えず、冗長な言い回しを削り、既存の文体(体言止め・「〜こと」「〜必要がある」等)に統一して文字数を減らす。

   a〜e を一通り適用しても 25KB を超える場合は、diff に無関係な既存項目も含めファイル全体を対象に c・d を追加適用する。

   統合・削除・分割を行った項目は、後で追跡できるよう手順8の報告で一覧化する。

8. **結果を報告する**
   - 確認した範囲(`<last>..<HEAD>` のハッシュ・コミット数)
   - `docs/spec/specification.md` に追加 / 更新した節の要約(追加した Mermaid 図・用語があれば併記)
   - 事実の欠落チェック結果(列挙 N 件 / 反映 N 件。反映しなかった事実があれば理由付きで列挙)
   - 「要確認」として残した項目があれば列挙する
   - `CLAUDE.md` のハマりポイントで統合・削除・分割を行った項目があれば一覧化する

## 注意

- このスキルは**コミットしない**。`docs/spec/specification.md` を編集するだけ。コミットが必要なら smart-commit スキルを使う。
- マーカーのハッシュは必ずルートリポジトリのコミットを記録する。
- `docs/spec/specification.md` は細部を確認するための正本(Markdown + Mermaid)とする。全体像を掴むための HTML ページや解説動画は、ユーザーから依頼があった場合のみ、この正本を元に別ファイルとして作る(正本に無い事実を足さない)。
