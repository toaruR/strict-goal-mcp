ルートリポジトリ(このプロジェクト自身)の変更点を読み取り、プロジェクトの仕様を `docs/specification.md` にドキュメント化してください。前回このスキルで確認したコミットを記録しておき、次回はそれ以降の差分だけを対象にします。

## 前提

- 差分の対象リポジトリ: ルート(このリポジトリ自身。git コマンドは通常どおり `git ...`)。
- 仕様ドキュメントと「最後に確認したコミット」の保存先: ルートの `docs/specification.md`(単一ファイル・追記更新)。
- 最終確認コミットは `docs/specification.md` の先頭に次の形式のマーカーで記録する:
  ```
  <!-- spec-doc:last-reviewed-commit=<commit-hash> reviewed-at=<YYYY-MM-DD> -->
  ```

## 手順

1. **前回確認コミットを取得する**
   `docs/specification.md` を読み、先頭の `spec-doc:last-reviewed-commit` マーカーからハッシュを取得する。
   - ファイルが無い、またはマーカーが無い場合は **初回** として扱う(後述)。

2. **現在の HEAD を取得する**
   `git rev-parse HEAD` で現在のコミットを取得する。
   - 前回確認コミットと一致する場合は「前回から新しい変更はありません」と伝えて終了する。

3. **差分を把握する**(並行実行)
   - 通常: `git log --oneline <last>..HEAD` と `git diff <last>..HEAD`
   - 初回(マーカー無し): `git log --oneline -20` と、現状を俯瞰するため主要ディレクトリ(`scripts/`・`src/` 等)の構成を `git ls-files` 等で確認する。
   - 差分が大きい場合はファイル単位で `git diff <last>..HEAD -- <path>` に分割して読む。

4. **コンテキストを読み込む**
   仕様を正確に書くため、関連ドキュメントを参照する。
   - `CLAUDE.md`(アーキテクチャ・ハマりポイント・知見)
   - `AGENTS.md`
   - `docs/` 配下の関連ファイル(実装計画・タスク管理など)
   - 既存の `docs/specification.md` の内容(重複記述を避け、整合させる)

5. **仕様を抽出してドキュメント化する**
   コミットメッセージと diff から「**何が・どう振る舞うか**」という仕様を読み取る。実装の手順ではなく仕様・挙動・設計意図を書く。
   - 画面 / API エンドポイント / データモデル(db.json) / 公開(HTML 書き出し) / 設定 など、対象ごとに見出しを分けて記述する。
   - 追加された機能は新しい節として追記、既存仕様の変更は該当節を上書き更新、削除された機能はその旨を反映する。
   - 不明点(diff だけでは意図が読めない箇所)は推測で断定せず「要確認」として明示する。

6. **`docs/specification.md` を更新する**
   - 先頭マーカーを今回の HEAD ハッシュ・本日の日付(CLAUDE.md の currentDate)に更新する。
   - 初回でファイルが無い場合は、マーカー + `# 仕様書` 見出し + 対象別の節という構成で新規作成する。
   - 本文は日本語で、既存 `docs/` のトーンに合わせる。

7. **`CLAUDE.md` の「ハマりポイント」を最適化する**
   このセクションは知見の記録ルールにより都度追記される運用のため、肥大化・重複・陳腐化が起きやすい。**目標: `CLAUDE.md` はファイル全体で 25KB 未満に保つ**(`wc -c CLAUDE.md` で確認)。今回の diff で触れた範囲を中心に、以下 5 種類の最適化を行う。

   - **a. 重複・類似項目の統合**: 同じ原因・同じ対処を指す複数の項目を 1 つにまとめる。内容は欠落させず、具体例や参照先はすべて残す。
   - **b. 陳腐化した項目の検出**: 今回の diff で変更・削除されたファイルや機能に関連する既存項目があれば、該当コードが今も同じ挙動かを `grep`/`git -C review-app diff` などで確認する。
     - 明確に解消済み(該当コード・設定が削除／修正済み)と確認できた場合のみ削除する。
     - 判断がつかない場合は**自動削除しない**。文末に `(要確認: 現状と一致するか未検証)` を付記し、手順8の報告に列挙する。
   - **c. 長大化した項目の `docs/` への分割**: 1 項目が目安 300〜400 字を超えている場合、詳細を対応する `docs/*.md` に移し、`CLAUDE.md` 側は 1〜2 行の要点 + `→ 詳細: @docs/xxx.md` のリンク形式に圧縮する(既存の `docs/*.md` 群の参照パターンに合わせる)。移し先の判断基準:
     - 既存の `docs/*.md` に明確に対応するテーマがあればそこに追記する(新規ファイル作成は避ける)。
     - どの既存ファイルにも当てはまらない新しいテーマの場合のみ、新規 `docs/*.md` の作成をユーザーに確認する。
   - **d. 既存 docs との重複圧縮**: `docs/` 配下の各ファイルを横断的に確認し、ハマりポイントの項目と**同じ内容がすでに詳しく書かれている**箇所があれば、CLAUDE.md 側は 1〜2 行の要点 + リンクに圧縮する(c と同様の圧縮だが、"今回新たに移す" のではなく "すでにどこかにある内容の重複を消す" 点が異なる。過去の記録時に docs 側へ移し忘れた項目や、後から docs 側に詳細版が書かれて二重管理になった項目を拾うのが目的)。
   - **e. 表現の簡潔化・文体統一**: 項目数・内容は変えず、冗長な言い回しを削り、既存の文体(体言止め・「〜こと」「〜必要がある」等)に統一して文字数を減らす。

   a〜e を一通り適用しても 25KB を超える場合は、diff に無関係な既存項目も含めファイル全体を対象に c・d を追加適用する。

   統合・削除・分割を行った項目は、後で追跡できるよう手順8の報告で一覧化する。

8. **結果を報告する**
   - 確認した範囲(`<last>..<HEAD>` のハッシュ・コミット数)
   - `docs/specification.md` に追加 / 更新した節の要約
   - 「要確認」として残した項目があれば列挙する
   - `CLAUDE.md` のハマりポイントで統合・削除・分割を行った項目があれば一覧化する

## 注意

- このスキルは**コミットしない**。`docs/specification.md` を編集するだけ。コミットが必要なら smart-commit スキルを使う。
- マーカーのハッシュは必ずルートリポジトリのコミットを記録する。
